# Aqua Guard - node pairing (protocol v2, gateway registry)

Status: **protocol, node firmware, gateway firmware (registry, portal, commands) and host tests are implemented (Phases 2-3).**
The node firmware has run on real hardware (flow node on an ESP32-C3); the gateway firmware has only been compiled and host-tested - see the checklists in `docs/TEST_PROCEDURE.md`.

> The Milestone 3 design (backend-mediated pairing, ESP-01S nodes, GMK-derived device secrets, uid/slot 4..12) is **retired**.
> Its sketches are archived in `firmware/legacy/`.

## 1. Identities

| Name | Example | Visible to users | Purpose |
|---|---|---|---|
| MAC | `34:85:18:AA:BB:01` | yes (sticker, portal) | hardware identity (ESP-NOW STA MAC). **Never a secret.** |
| pairing code | `ABCD-EFGH-JKMN` | yes (sticker) | the secret. 12 symbols = 60 bits, generated by the node at first boot, kept in NVS. **Survives factory reset** (it is printed on the sticker); changes only with the serial command `regen-code`. |
| node number | "Node 2" / "Rain 1" | yes | assigned by the gateway registry, numbered **per type**; survives *replace*. |
| radio slot | `3` | **no** | internal ESP-NOW address (header `nodeId`), 1..`AQUA_MAX_SLOTS` (12). |

Code alphabet: Crockford base32 (`0-9 A-H J K M N P-T V-Z`; no I, L, O, U). Typed input ignores dashes, spaces and case and maps
`O->0`, `I/L->1`. 8 symbols (40 bits) could be brute-forced offline from one captured handshake; 12 cannot practically.

## 2. Keys

```
PSK   per-site key compiled into every device (aqua_secrets.h).  Tags ONLY discovery + the pairing handshake frames.
Kp    = f(code, MAC)             pairing key. Known to the node and (from the QR / manual entry) the gateway. Never transmitted.
Kn    = KDF(Kp,'N',salt)         per-node key. salt = 8 random bytes chosen by the gateway at registration, sent in ACCEPT.
Kop   = KDF(Kn,'K',bootId)       per-boot data key. Tags DATA / ACK / NACK / HEARTBEAT / UNPAIR of that node.
Kcmd  = KDF(command key,'C')     backend <-> gateway commands / events (AQUA_CMD_KEY = AQUAGUARD_CMD_KEY).
```

All primitives are SipHash-2-4 (already used by the frame tags). `tools/generate_secrets.py` creates PSK, PMK, LMK and the command
key randomly and writes the command key to **both** `aqua_secrets.h` and `backend/.env`. The example template is all-zero and marked
`AQUA_SECRETS_ARE_EXAMPLE`: every firmware build refuses it, and the nodes refuse a weak PSK at boot.

Because Kn depends on the node's own code, copying one node's flash exposes **that node only**; the shared PSK cannot forge DATA.

## 3. Handshake (reuses the existing frames)

```
node (unpaired / rebooted)            gateway (registry has the MAC + Kp)
 DISCOVERY_REQUEST (PSK)  ──────────▶ DISCOVERY_RESPONSE (real channel + MAC)        existing channel discovery
 PAIR_ANNOUNCE (PSK, no secret) ────▶ registered MAC? no -> listed as "nearby", NEVER paired automatically
                                      yes -> CHALLENGE (unicast, 8 random bytes, max 1 per second per node)
 RESPONSE = MAC_Kp('R',mac,boot,chal) ▶ verify (constant time)  -> fail: event F, no key installed
                                      Kn, Kop derived; entry pending -> paired
 ◀── ACCEPT = slot, salt, MAC_Kp('A',mac,boot,chal,slot,salt)    the node verifies the GATEWAY knows Kp too (mutual proof)
 DATA / HEARTBEAT (Kop) ────────────▶ ACK / NACK (Kop)  (configuration - pulses/L, TX-power flag - rides on the ACKs)
```

* A node repeats the handshake after every reboot or link loss (new boot id -> new Kop); a rebooted gateway re-learns the sessions the same way.
* **Remove**: the gateway sends `UNPAIR` (tagged with the node's session key), frees the slot, and the node restarts unpaired. If the node is
  unreachable the slot is freed anyway and the node later shows up as *nearby*. **Replace** swaps MAC + Kp under the same slot and number.
* Pulses counted before the first join of a boot are not part of the volume record (cumulative counter is baselined at the join).

## 3a. Reset vs. new code

| Action | Pairing state, keys, calibration | Pairing code / QR sticker |
|---|---|---|
| BOOT hold 5 s (after boot) | "paired" forgotten, node re-enters pairing | **kept** |
| BOOT hold 15 s = factory reset | all cleared (paired flag, calibration, TX-power flag) | **kept** - the sticker stays valid |
| Serial `regen-code`, then `regen-code confirm` within 30 s | cleared as above | **NEW code** (printed with its QR); the old sticker is useless, print a new one, and the old registration in the gateway must be removed and re-added |

Per-node keys are derived from the code, so a node keeps its identity across factory resets and gets a new identity only through `regen-code`.
Anything other than the exact confirmation (or a confirmation older than 30 s) cancels. Gateway side: a factory-reset node simply shows up
as *nearby* again; add it with the same sticker.

## 4. QR payload

```
http://192.168.4.1/add?v=1&mac=AA:BB:CC:DD:EE:FF&code=XXXXXXXXXXXX&type=flow     (a phone camera opens the portal's add page)
AQG1;AABBCCDDEEFF;XXXXXXXXXXXX;flow                                                (compact)
```
`type` = `flow` | `rain`. Parser: `aquaQrParse` (firmware), `tools/aqua_qr.py`, portal JS / web app (later phases). All implementations must
pass `tests/qr_vectors.json` (valid, lower-case, encoded colons, missing fields, wrong version, bad MAC / code / type).
Stickers: `python tools/make_node_labels.py --serial-log boot.txt` (QR + MAC + code in plain text for manual entry).

## 5. Signed gateway <-> backend messages

* Events gateway -> backend, `<prefix>/pairing/event`: `AQE1 <D|O|F> <number> <mac12> <type> <fw> <ch> <rssi> <boot8> <slot> - - <epoch> <tag16>`
  (same envelope and SipHash tag as Milestone 3; the two challenge/response fields are now always `-` because the backend never sees Kp).
  `D` = node nearby, `O` = handshake ok, `F` = failed.
* Commands backend -> gateway (add / rename / remove / replace / calibrate) are single text lines, **`AQC2`**, published on
  `<prefix>/gateway/cmd` or `<prefix>/<gw>/gateway/cmd`:
  `AQC2 <ts> <nonce24hex> <op> <type> <number> <mac12|-> <pplX10|-> <flags|-> <namehex|-> <codeEnc24hex|-> <tag16hex>`
  with `op` = `A` add, `N` rename, `R` remove, `P` replace, `C` calibrate; `type` 1 = flow, 2 = rain; `number` = display number (0 for add);
  `namehex` = UTF-8 name as hex. **The pairing code is encrypted**: ChaCha20 (RFC 8439), key = `KDF(site key,'E',0) || KDF(site key,'E',1)`,
  nonce = the 12 random nonce bytes of the message (unique per message), block counter 0, plaintext = the 12 ASCII code symbols. The tag is
  SipHash-2-4 with Kcmd over every character before the last field (8 bytes, little-endian, lower-case hex), so op, number, MAC, name and
  ciphertext cannot be altered. Backend: Python `cryptography` `ChaCha20(key, counter||nonce)` with a 16-byte nonce = `00000000` + the 12 nonce bytes.
  A reference vector lives in `tests/cmd2_vectors.json` (the C++ test and the Phase 4 backend tests must both reproduce it).
* Gateway rules: it needs **NTP time** (without it every command is refused with `gateway_time_not_synced`, "fail closed"); `|ts - now| <= 300 s`;
  `ts` never older than the last accepted command; a nonce must not repeat (last 8 remembered). Commands that carry a code (add, replace) are
  **refused (`tls_required`) unless the MQTT connection uses TLS with a verified certificate** (or the dev flag "allow plain" is set in the portal).
  Every command answers on `<prefix>/<gw>/gateway/cmd/result`.
* The registry on the gateway is authoritative; the backend only mirrors the retained `<prefix>/<gw>/nodes/registry` and sends commands.

## 6. Known limitations (documented, not hidden)

* **Pairing codes are stored in plaintext in gateway NVS** (and the node's own NVS). NVS flash encryption would protect them against a
  physical flash read-out - possible later step. The Kp (not the code) is what the gateway core uses at runtime.
* The "gateway secret" contribution to Kn is the random **salt**, which is sent in clear in ACCEPT: Kn's security rests on the pairing code,
  not on the salt. (A salt unknown to an eavesdropper would require encrypting it, which the protocol does not do.)
* Kp is derived with SipHash, not a password-hardening KDF; the 60-bit random code is what makes offline guessing impractical.
* A node whose flash is read out reveals its own code and therefore its own Kn / session keys.
* No hardware verification yet: ESP-NOW on the ESP32-C3 SuperMini, antenna range, LED polarity and the ADC divider are untested.
* Rain node (ESP32 DevKit): BOOT (GPIO0) and the onboard LED (GPIO2) give the same re-pair / factory-reset / status behaviour as the C3 node; the LED polarity (assumed active HIGH) is unverified.
* ESP-NOW link encryption stays off by default. If you turn it on (`AQUA_ESPNOW_ENCRYPT=1`) the ESP32 allows only about 6-7 encrypted peers.
